Step 1 of 7

Connect your Git platform

Every Maia project is backed by a Git repository. Use Maia Hosted Git, where Maia creates the repository for you, or connect your own on GitHub, Azure DevOps, GitLab or Bitbucket.

For your own repository, you install the Maia app once. Maia connects over OAuth, honors the permissions you set in your Git platform, and you can revoke its access at any time.

Maia capabilities

Maia Hosted GitGitHubAzure DevOpsGitLabBitbucket

The connection is fixed per project. Connecting your own repository is available on specific Maia plans, and GitHub Enterprise Server isn’t supported. The setup guide below walks through the connection.

Step 2 of 7

Branch from main

Develop on a named branch, not on main. In Designer you pick the branch to start from, usually main, and the new branch appears instantly because a branch is only a pointer to a commit.

A new branch starts as a local branch in your workspace, so you can experiment without affecting anyone. It stays private until you push it. Branches created in your Git platform appear in Maia automatically.

Maia capabilities

Add branchLocal and remote branchesDefault environment

Match the strategy to your team: feature branching suits teams of three or more, and trunk-based development suits smaller teams.

Step 3 of 7

Build and commit

Build or edit pipelines on your branch. Compare changes to review what you’ve done, then commit to save a snapshot.

A commit lives in your online copy in Designer, and nobody else sees it yet. Designer has Git built in, so there are no local files or command line to manage.

Maia capabilities

Compare changesCommitRevertReset branch

Maia context files carry your standards across branches. Follow the recommended Git workflow so they travel with your changes.

Step 4 of 7

Push to sync out

Push sends your commits to the remote repository so your team can see them. Your online copy isn’t synced automatically in either direction, so a push is how your work reaches the remote.

You can also tick Publish on a push to build an artifact for an environment. After a push, Designer shows a link to create a pull request in your Git platform.

Maia capabilities

Push local changesPublishPull request link

Pull before you push, so your branch includes everyone else’s latest work.

Step 5 of 7

Open a pull request and merge to main

Pull requests happen in your Git platform, so its review, checks and approval rules apply. GitHub, Azure DevOps and Bitbucket call them pull requests, and GitLab calls them merge requests.

When your team approves, merge into main in the platform. You can open your pull requests from the branch menu in Designer.

Maia capabilities

View pull requestsYour platform’s approval workflow

Merge from branch in Designer also combines branches, and helps you resolve conflicts.

Step 6 of 7

Pull to sync in

Pull brings changes other people have pushed into your online copy, so your main and your branch match the remote. Pull often, and before you start new work.

If two branches changed the same pipeline, you choose which version to keep: Keep local or Keep remote when merging, and OURS or THEIRS when pulling.

Maia capabilities

Pull remote changesMerge from branchConflict resolution

A merge from a local source stays in your workspace until you push it.

Step 7 of 7

Publish, promote and run

Publishing builds an artifact: an immutable, versioned package of your pipelines, built from a specific commit and deployed to an environment. Git holds your source, and the artifact is what runs.

Promote the same artifact from Development to Test to Production, and point schedules at the latest version or pin one. CI/CD tools can do the same through the Maia API, which can create, promote and disable artifacts, create schedules, run pipelines and review pipeline quality.

Maia capabilities

ArtifactsEnvironmentsSchedulesMaia APIPipeline quality review

Promoting needs an environment role with the Promote Artifacts permission. Branches can’t be managed through the API, so you create and manage them in Maia.

Setup guide

Before you connect

You set up the connection once, when you create a project. After that, every user authorizes their own account the first time they use a Git action.

Before you start

  • Your Maia plan includes connecting your own Git repository.
  • You have an organization account on your Git platform, not a personal one.
  • Someone can install apps and create a repository there.
  • The repository has a main branch.

Good to know

  • Maia connects with OAuth and honors the permissions set in your Git platform.
  • Maia stores each user’s access and refresh tokens in the Matillion secure vault, and nothing else sensitive about the user.
  • You can revoke Maia’s access at any time from your Git platform.

Setup guide

Connect Maia to your repository

  1. In GitHub
    Create a repository

    In your GitHub organization, create a new repository and initialize it with a README file. That creates the main branch, which Maia requires. Use the repository only for your Maia pipelines.

    Using an existing repository? Only its main branch syncs to the Maia project, and its other branches are ignored.

  2. In GitHub
    Install the Maia app

    Open the Maia Integration app on GitHub Marketplace and install it in your organization account, not a personal account. Choose Only select repositories and pick the repository from step 1. The app needs read and write access to repository contents and to workflow files. You only install it once.

    Check the install at github.com/organizations/<your-org>/settings/installations.

  3. In GitHub
    Check roles and network access

    Give everyone who will build pipelines at least the Write role on the repository. If your organization uses an IP allowlist, add Maia’s Git IP addresses for your region, or turn on GitHub’s setting that adds the IP addresses of installed apps.

  4. In Maia
    Create a project

    Go to Projects and choose Add project. Enter a name, description and data platform, then choose Advanced settings. Pick Full SaaS or Hybrid SaaS, create your environment, and continue to the Git provider step.

  5. In Maia
    Authorize GitHub

    Select GitHub and continue. A new tab opens, where you click Authorize Maia. If you sign in to GitHub with SSO, click Authorize, not Continue. Back in Maia, confirm your account in the dialog.

  6. In Maia
    Select the repository

    Choose your repository from the list of repositories you’ve granted access to, then click Finish. Maia doesn’t create repositories, so it has to exist already. Your project opens with Branches, Environments, Artifacts, Schedules and more.

  7. In Maia
    Invite teammates (optional)

    Add them as project users. They should be members of the same GitHub organization where the app is installed.

  8. In Maia
    Confirm the connection

    Open Branches and look for main. Create a branch, commit and push, then check it appears in GitHub. Create a branch in GitHub and check it appears in Maia.

  1. In Azure DevOps
    Create a repository

    In your Azure DevOps organization and project, create a new repository and initialize it with a README file. That creates the main branch, which Maia requires.

    Using an existing repository? All of its existing branches appear in Maia.

  2. In Azure DevOps
    Check access and network access

    Users need to be in the Contributor security group with Basic access at minimum, or have Read and Write permissions if you use custom groups. If Entra Conditional Access limits IP addresses, add Maia’s Git IP addresses to a named location it allows.

  3. In Maia
    Create a project

    Go to Projects and choose Add project. Enter a name, description and data platform, then choose Advanced settings. Pick Full SaaS or Hybrid SaaS, create your environment, and continue to the Git provider step.

  4. In Azure DevOps
    Install the Maia app

    Select Azure DevOps. You’re redirected to sign in with a work, business or school account and to consent for the app. You only install it once per Azure tenant.

    If consent needs an admin, invite them to your Maia organization and have them start project creation as far as the repository step. They can then grant consent for “Maia for Azure DevOps” under Enterprise applications in the Azure portal. Don’t use Microsoft’s suggestion to sign in with admin credentials, because that captures the admin’s token instead of yours.

  5. In Maia
    Select the repository

    Choose your repository from the Project repository list and click Finish.

  6. In Maia
    Invite teammates (optional)

    Add them as project users. They should be members of the same Azure DevOps organization.

  7. In Maia
    Confirm the connection

    Open Branches and look for main. Create a branch, commit and push, then check it appears in Azure DevOps.

GitLab and Bitbucket follow the same pattern, each with its own prerequisites guide in the Maia documentation.

How syncing works once you’re connected

Pushes and pulls are explicit

Your online copy in Designer isn’t synced automatically in either direction. Push sends your commits to the repository, and Pull brings changes in.

Branches show up on both sides

Branches you create in Maia appear in your repository once you push them, and branches created in your Git platform appear in Maia.

Each user authorizes

The first Git action prompts a user to authorize. Anyone who picked the wrong account can reauthorize from the project page.

Branching strategies

Choose the strategy that fits your team

  1. Feature branching

    Each change gets its own short-lived branch from main and is reviewed through a pull request. Recommended for teams of three or more, because developers work in isolation.

  2. Trunk-based development

    Everyone integrates into main in small steps, and main stays deployable. It suits smaller teams that want simplicity and speed.

Releases

Git holds the source. Artifacts are the release.

  1. Git: your source

    Editable pipelines and their full history. People change it every day on branches, and pull requests control what reaches main.

    Branches and pull requests

  2. Artifacts: what runs

    A frozen, versioned copy built from a specific commit. It never changes, it can be promoted between environments, and schedules run it, so production is shielded from unfinished work.

    Immutable and promoted

CI/CD and the API

Automate the release path

The Maia API is a REST API over HTTPS, so any CI/CD tool that can call it can take part. The OpenAPI specification is available to import into your API client.

  1. Create and promote

    Create an artifact from a commit, promote it to other environments, or disable it. A Python script is available to simplify artifact creation.

  2. Schedule and run

    Create schedules that use the latest artifact or a pinned version, with variable overrides, and run and monitor pipelines.

  3. Check quality

    Review pipelines against your pipeline quality rules as a CI check, using the same rules as the Review feature in Designer.

Branches can’t be managed through the API. You create and manage them in Maia.

Common questions

What teams ask about Git and DevOps

Can we use our existing GitHub or Azure DevOps repository?

Yes, on plans that include connecting your own Git repository. You install the Maia app in GitHub or your Azure tenant once, then choose the repository when you create a project. Maia honors the user permissions you set in your Git platform.

Can we change the repository later?

A project’s connection is fixed once it’s made, and you can’t disconnect it or switch Git platforms in place. If you need to move a project to a different repository or provider without recreating it, use the Repository Migration API.

Do developers need a local Git client?

No. Designer has Git built in, and you work in an online copy of the repository, so there are no local files or command line. You can still use your provider’s own tools alongside Maia.

Do our pull request rules still apply?

Yes. Pull requests are created in your Git platform after a push, so its reviews, checks and approvals apply. Designer links you there and can list your pull requests.

What happens when two people change the same pipeline?

When you merge or pull, Maia lists the pipelines in conflict and you choose which version to keep. A branch can’t hold two pipelines with the same name, so one version wins for each conflicted pipeline.

Is an artifact the same as what’s in Git?

No. Git holds your editable source. An artifact is a frozen, versioned copy built from a specific commit, and it’s what schedules run. That shields production from later edits and unfinished work, and it makes rollbacks straightforward.

Can we automate releases from CI/CD?

Yes. The Maia API is a REST API over HTTPS, so any CI/CD tool that can call it can create, promote and disable artifacts, create schedules, run pipelines and review pipeline quality. The DataOps best practices guide includes a GitHub Actions example.
